    ADR-0009: World generators and stochastic parameter distributions¶
    Status Accepted — amended 2026.11 (review pass 10: network plan, English names, reproducibility, measurement wiring); see the amendment at the end of this document
    Date 2026-05-08
    Deciders Project maintainers
    Scope groundfield.generators (new subpackage); parameter
    sweep / Monte Carlo studies; foundation for the
    ParameterSweep API

    Context¶

    groundfield now has the full physics stack (image / image_2layer / image_nlayer / cim / mom / mom_sommerfeld / bem / fem, inductive coupling, Carson, Sommerfeld, cross-layer, distributed conductors) and a closed bridge to groundinsight via the rho-f fit and the BusType exporter (ADR-0008). What is missing is the factory layer that converts high-level parameters (number of single-family houses \(n_\text{EFH}\), small/medium commercial buildings, cable-cabinet quota, two-layer soil with \(\rho_1, \rho_2, h_1\)) into a fully populated World. Without it each parameter combination is hand-coded; with it the same combination is one line and a parameter sweep across the table is a straightforward outer loop.

    The user request additionally asks for two non-negotiable features:

    1. Multiple generators are anticipated (TN-Ortsnetz first, but later e.g. an MV-strand generator, or an open-building-map-driven generator). The framework must be plug-extensible, not a single hard-coded function.
    2. Stochastic parameters. Each numeric input may be fixed or sampled from a distribution (Normal, Weibull, LogNormal, Uniform, ...). Every sample must be reproducible (RNG seed) and the resolved configuration must be persistable (so a Monte Carlo run can be re-executed bit-exactly).

    Decision¶

    Architecture: ABC + per-generator Pydantic config¶

    class WorldGenerator(ABC, Generic[C: GeneratorConfig]):
    cfg: C
    def __init__(self, cfg: C, *, rng: int | np.random.Generator | None = None): ...

    @abstractmethod
    def build(self, cfg: C | None = None) -> World: ...

    def sample_world(self, rng=None) -> tuple[World, C]: ...

    Every concrete generator (TnNetworkGenerator, future MvStrandGenerator, ...) ships its own GeneratorConfig subclass — a Pydantic v2 model with full type information and defaults. The generator class is thin; it takes a config, optionally samples any stochastic fields via cfg.sample(rng), and constructs the World.

    Rationale (vs. a flat function build_tn_ortsnetz(**params)):

    • Pydantic gives us validation, JSON dump/load, and IDE-grade autocompletion for free.
    • Sweeps and CLI tools talk to the abstract WorldGenerator interface; no per-generator dispatch.
    • Persisting a config is a one-liner; the resulting JSON is the experimental record of a single run.

    Stochastic parameters: Distribution Pydantic classes¶

    Every numerical field of a GeneratorConfig is typed as a discriminated union T | Distribution where Distribution is the abstract base of the seven first-class distributions:

    Class Backend Use case
    Constant(value) trivial placeholder for "act like a distribution"
    Uniform(low, high) np.random.Generator.uniform bounded continuous
    Normal(mean, std, truncate_low?, truncate_high?) rejection sampling engineering tolerances
    LogNormal(mu, sigma) (or mean_phys, std_phys) rng.lognormal resistivities, sizes
    Weibull(shape, scale) rng.weibull × scale wind/wear/lifetime
    Discrete(values, weights?) rng.choice default grid n_efh ∈ {5,10,30,80,200}
    Categorical(values, weights?) rng.choice (string) electrode-kind mix

    Every distribution is a Pydantic v2 model with a .sample(rng) -> Any method. Distributions are JSON-serialisable through a discriminator field kind: Literal["uniform", "normal", ...]. A run can therefore be persisted as

    {
  "n_efh": {"kind": "discrete", "values": [5, 10, 30, 80, 200]},
  "rho_1": {"kind": "lognormal", "mu": 5.0, "sigma": 0.7},
  "h_1":   {"kind": "uniform", "low": 2.0, "high": 10.0},
  "trafo_ring_radius_m": 4.0
}

    and replayed bit-exactly given a seed.

    Resolution: Union field + cfg.sample(rng) traversal¶

    GeneratorConfig.sample(rng) walks self.__dict__ and replaces every Distribution instance with its sampled value, recursing into nested GeneratorConfig fields. The result is a resolved config — same type, but every field is a constant.

    WorldGenerator ships an _assert_resolved(cfg) helper that raises ValueError when a config still carries Distribution fields. Whether to call it inside build is a per-generator choice:

    • Strict mode — build calls _assert_resolved and refuses any unresolved config. Stochastic configurations must go through sample_world(rng) (or a manual cfg.sample(rng)) first. Best for generators where every distribution is conceptually a Monte-Carlo axis (one draw per realisation).

    • Lazy mode — build does not call _assert_resolved and resolves distributions opportunistically as values are needed. Top-level numeric distributions get one draw per build call; per-instance distributions (e.g. a Categorical electrode kind that the user wants drawn afresh per house) survive cfg and are sampled inside the relevant inner loop. TnNetworkGenerator uses this mode so that Categorical(values=["foundation", "rod"]) in house_electrode.kind produces a real per-house mix when gen.build(cfg) is called directly.

    Both modes coexist at the framework level. The user picks via the generator they instantiate; WorldGenerator.sample_world works in either case (it always pre-resolves through cfg.sample).

    This keeps the type system simple: one config class per generator, not two parallel "stochastic" and "deterministic" classes. The trade-off is documented per generator: callers of sample_world on a lazy-mode generator get one electrode kind for all houses (because cfg.sample collapses the Categorical), while callers of build directly get the per-house mix.

    Spec layer: composable building blocks¶

    The first concrete generator (TnNetworkGenerator) sits on top of five reusable spec layers. Each layer is independently JSON-roundtrip-able and accepts distributions on every numerical field; future generators (MV strand, OSM-driven distribution network) reuse the same layers without code duplication.

    1. electrode_specs — single-electrode specifications. Discriminated union ElectrodeSpec with four members: RodElectrodeSpec, RingElectrodeSpec, StripElectrodeSpec, FoundationElectrodeSpec. Common fields: presence_prob (Bernoulli per realisation), offset_xy_m (translation relative to the site centre). Geometry parameters per kind are float | Distribution. Helper rod_circle(n, radius_m, …) returns N rods arranged on a circle — typical layout for the substation Tiefenerder.

    2. grounding.GroundingSystemSpec — multi-electrode installation. Holds an ordered electrodes: list[ElectrodeSpec]. The method build_at(world, site_xy, name_prefix, rng) materialises every present electrode (Bernoulli on presence_prob), translates by offset_xy_m, registers it with the world, and bonds all present electrodes into one cluster via bare-copper conductors. Returns the anchor (first present electrode) so the caller can wire PEN / sources into the cluster.

    This abstraction is shared by the substation, every cable cabinet, and every building. A "ring + 4 rods + strip + foundation" substation is one GroundingSystemSpec with seven electrodes. A "70 % of houses have a foundation, 30 % also have an additional rod" study sets presence_prob=0.3 on the rod spec inside the residential BuildingTypeSpec.

    3. placement — pluggable site placement on the 2-D plane. Discriminated union PlacementSpec with two members in v1: ManhattanGridPlacement (regular street raster, optional per-site jitter) and ExplicitPlacement (caller-supplied list of \((x,y)\) tuples — useful for replaying a real map slice or for deterministic small reference cases). Each implements generate(n, rng) -> list[(x, y)]. Random scatter and cluster placement are deferred to a follow-up.

    4. soil_specs — soil-model specifications. Discriminated union SoilSpec with three members: HomogeneousSoilSpec, TwoLayerSoilSpec, MultiLayerSoilSpec. Each carries the same fields as the underlying SoilModel but allows distributions; the method to_soil(rng) returns a fully numeric SoilModel. A two-layer soil is the default.

    5. building.BuildingTypeSpec — building type definition. Bundles a name, a GroundingSystemSpec, and an optional plot_size_m. Multiple types coexist in TnNetworkConfig.building_types; the count per type is set via TnNetworkConfig.building_counts: dict[name, int | Distribution]. The default catalog returned by default_building_catalog() ships typical entries for residential, small_industry, medium_industry, and large_industry.

    Topology: medium detail (TnNetworkGenerator v2)¶

    The generator composes the five spec layers into:

    • A substation at cfg.substation.position with a GroundingSystemSpec of arbitrary composition.
    • A configurable number of buildings (per type, per count) placed via cfg.placement. Each building runs its own GroundingSystemSpec.build_at — per-instance sampling of Bernoulli presence and geometric distributions, so a stochastic config naturally produces a heterogeneous fleet.
    • \(n_\text{KVS} = \lceil q \cdot n_\text{buildings} / 100 \rceil\) cable cabinets (or a fixed_count override) placed via their own cfg.kvs.placement. Each KVS has its own GroundingSystemSpec.
    • A PEN backbone as a distributed conductor (ADR-0003): substation → each KVS, each building → its nearest KVS (Manhattan metric). Configurable coupling_to_soil ("isolated" | "galvanic") and inductance_model per ADR-0004.
    • A current source attached to the substation cluster.

    This level of detail captures every research question (remote-injection influence, inductive coupling between measurement leads and PEN/MV shield, Carson relevance below 1 kHz, soil-layering monotonicity). Higher fidelity (real street polygons, plot-level layouts, foundation-shape diversity) is deferred to a follow-up generator that will read from open building-map data.

    Validation programme¶

    1. Distributions — each subclass passes:
    2. reproducibility: same seed → identical sample sequence;
    3. statistical sanity: 10 000 samples reproduce the analytical mean and variance to within 5 %;
    4. JSON round-trip: model_dump_json + model_validate_json reproduces the distribution bit-exactly;
    5. bound enforcement: Normal truncation never returns out-of-band values.
    6. Base framework —
    7. cfg.sample(rng) resolves all Distribution fields to constants and leaves non-distribution fields untouched;
    8. cfg.has_distributions() is honest;
    9. in strict-mode generators, build(cfg_with_distributions) raises a clear error via _assert_resolved;
    10. in lazy-mode generators (e.g. TnNetworkGenerator), build(cfg_with_distributions) is supported and produces per-instance variation where designed;
    11. JSON round-trip preserves the config.
    12. TnNetworkGenerator —
    13. the smallest preset (5 EFH) builds a World that solves successfully with image_2layer;
    14. the largest preset (200 EFH) builds a World whose segment count stays below the configured budget (default 4 000);
    15. parameter sweep over \(n_\text{EFH} \times \rho_1\) produces monotonic cluster-impedance trends consistent with Dwight 1936 (asymptotically \(Z \propto \rho_1\) at low \(f\));
    16. the same seed produces a bit-exact identical world over repeated calls.

    Consequences¶

    • The factory layer is now in place. The remaining roadmap items (ParameterSweep API, building-map ingestion) plug into the abstract WorldGenerator interface without further refactoring.
    • groundfield gains a scipy dependency runtime use of scipy.stats (already a transitive dep through scipy itself; no pyproject change).
    • The Generic[C] typing means tooling (mkdocstrings, mypy) keeps working for users of any generator.
    • The discriminated-union JSON format is versionless for now; if the distribution catalogue changes incompatibly we will bump to a schema_version similar to ADR-0008.

    Amendment 2026.11 — one network plan, English names, reproducible draws, the field wiring of a measurement (review pass 10)¶

    Findings 10.05, 10.12–10.14, 10.17, 10.38, 10.39, 10.53–10.55, 10.69 and 10.78.

    1. One plan, one materialiser. Both front-ends — TnNetworkGenerator (configuration-driven) and the footprint-driven layout builder — now produce a pure-data NetworkPlan, and one materialiser turns it into a World (foundations, concrete shells, junctions, measurement loop, sources). The physics of the two families can no longer diverge (10.78). The layout builder is the package groundfield.generators.layout.
    2. English names. German identifiers are replaced with deprecated aliases (removal no earlier than 2027.5): OrtsnetzLayout → LvNetworkLayout, KVS → cabinet (CabinetConfig, StarCabinetTopology, add_cabinet, …), capitalised unit suffixes → lower case (source_magnitude_a). Spec fields use lower-case unit suffixes; the soil specs mirror the literature symbols of their soil models (rho, rho_1, h_1) (10.69). Old configurations and pickles load.
    3. Reproducibility. cfg.sample(rng) resolves every distribution, also in nested specs; sample_world(rng) routes the per-site draws of the build to rng; the penetration mask is keyed by the outline when a footprint has no osm_id; jitter_m accepts a distribution (10.53, 10.55). Successive build() / plan() calls draw successive realisations of the generator's stream; TnNetworkGenerator.build() right after plan() (no rng=, nothing drawn since, the same configuration) materialises the plan plan() returned instead of drawing a second realisation, which differs under placement jitter (audit W3R2B).
    4. Geometry. Layout foundations follow the building footprint (10.54); rotated mesh foundations are polylines split at every crossing (10.39); every rectangular foundation is one wire per line at every angle (audit A2G-04 for meshes, user decision Q38 for rectangles without cross-braces, which were one grid mesh when axis-aligned); a rectangle at a multiple of 90° is rotated with the exact cosine and sine, so its coordinates carry no round-off and its local −y side stays the anchor (audit D3B-04; up to then it was the axis-aligned rectangle with swapped sides, 10.39, whose anchor is another side); PenConfig.depth_m is honoured; measurement leads run horizontally at their configured depth (10.55).
    5. Network wiring. PEN cable joints are leakage-free junction nodes instead of 5 cm pseudo-rods (10.38). Every cabinet has its own cable; a service drop taps the cable that feeds its building (10.38). Every conductor routed to a foundation ends at the point of that foundation nearest to it (user decision Q41): a service drop is the closest pair in plan of its feeding cable and the foundation wires, a cable leaving a substation or cabinet with a foundation starts at the foundation's point nearest to the next node, the conductor is attached to the wire that holds the point (PlannedContact), and a building that a cable crosses is joined to it and fed by it, without a drop — a cable of its feeding path, every trunk of the radial topology, and in the star topology the main that crosses it, whose cabinet then feeds it (the nearest of them, ties to the lower index; a main that does not feed the building stays unjoined, audits R4A-02, R4B-01; a cable that touches the foundation at a node and crosses it elsewhere is joined where it crosses, R5A-03); a drop whose closest pair lies at such a joint starts there on the cable (R4A-01), a drop from a node does not run along a trunk or another main farther than one minimum section, 1 cm (R4B-01; "along": both ends of a section within 1 cm of the drop's line, R5A-01), and the layout builder keeps its taps on the layout polyline, clipped at the projection of a site's foundation contact, so none lies inside a site foundation (R4A-03, R5A-02); the leading run of waypoints inside the start site's closed electrodes and the trailing run inside the end site's are part of those sites (audit R6A-01: a router corner inside a 2 m cabinet ring was a node that houses tapped, 82 of 2 540 drops of 200 random layouts), and every other passage of the cable through the substation's or a cabinet's closed electrodes joins the cable to that site where it enters and where it leaves it (audits W1B-03, W1B-04: a tap inside a passed cabinet's ring; a leg that came back through its start site lost its taps); ties go to the lowest wire index, then to the smallest arc position along the wire. Since user decision Q43 the same nearest-point rule holds for every horizontal earth electrode of a site — a RingElectrodeSpec circle (the default substations, met at the exact point of the circle) and a strip, the nearest of all of them at a site with several (site_contact_wires) — and only a site with rods alone keeps the head of its first rod. A drop is straight: it may pass over other buildings' foundations, 0.2 m above their wires (default grids of 10 to 200 houses: 0 … 100 % of the drops; star 30 houses all 20 drops, 5 m each, 100 m); a drop has no inductive coupling to an electrode's wires in the field model, and moving those drops 1 m aside changes the input impedance by at most 0.006 % with an insulated PEN and by up to −0.40 % with a bare one; drops keep the shortest connection and are not routed around foundations (user decision Q42). Before, every conductor ended at the connection point of the site's anchor — a corner of a rectangular foundation since A2G-04 / Q38 — so 47 of 282 drops of a ring-house test set ran along a side of their own foundation and houses beyond their cable were connected across the house (audit D3A-02). Everything attached by name keeps the connection point. Cabinets per building group (user decisions Q22 and Q35): the star topology places one cabinet per building group, at the far end of the houses it feeds — the buildings are cut into runs of consecutive bearings around the substation (from the widest angular gap, sizes differing by at most one, StarCabinetTopology.group_buildings), and each cabinet stands on the ray through its group's centroid, CabinetConfig.end_clearance_m (1 m) beyond the group's electrodes, rods included, plus the plan extent of its own grounding — or, when it would stand there farther than CabinetConfig.max_far_end_gap_m (20 m) from its houses (a wide group), on the ray through the group's far-end building, 1 m beyond it — and raises when it would come closer than end_clearance_m to another site (audits W1B-01, W1B-02: the centroid ray of a group of about 180° led 50.4 m past its houses; the threshold is a step, kept for 2026.11 by user decision D7 — a group that crosses it moves its cabinet by up to the width of the group, 141.8 m in the 50-house grid with its house columns 32.0 / 32.2 m apart, X at 1 kHz −22 / −19 % — and the plan records per cabinet which rule placed it, PlannedSite.cabinet_rule and centroid_ray_gap_m, audit W1R2-02; end_clearance_m must be smaller than max_far_end_gap_m, audit W1R2-09) — instead of on a fixed strip along the substation row (both cabinets of the default 30-house grid stood west of the substation, the eastern houses got drops of 3.5 … 106.5 m from it); a given CabinetConfig.placement keeps the former positions and the nearest-cabinet rule. In the radial topology a building in a substation slot taps its feeder's trunk instead of getting its own line from the substation. The fall-of-potential measurement is wired as in the field: instrument terminals meas_H / meas_S as junctions, the feed lead from meas_H to the auxiliary electrode, the probe lead to meas_S, one two-terminal source from the station to meas_H, and the reading measured_impedance(result) (10.17).
    6. Concrete. Encased foundations carry the shell coefficient on every wire, the cross-braces of a mesh foundation included (DIN 18014, user decision Q20); no shell resistance is put on PEN drops; concrete_model has no effect and is deprecated (user decisions Q21 and Q38; ADR-0012 amendment 2026.11).
    7. OSM ingest. Overpass requests and responses are bounded and validated before anything is cached (10.05).
